# Changelog

## 1.4.1

The first round of the company's test (searcio-demo.webhead.dev, 1.4.0, posts, pages and a custom type, no WooCommerce) found what follows. What is the service's is in `service-requests.md` (15-23), what is the framework's in `framework-requests.md`.

- **A password-protected post is no longer indexed with its text.** It is published, with `post_password` set, and `Document_Builder::is_indexable()` asked only for the `private` status, so with "Also index private & password-protected items" off its text was in every visitor's search window and the shopping assistant answered from it. It is now indexed only with the private ones. The upgrade step `Unindex_Password_Protected_Posts` queues the protected posts 1.4.0 indexed (`Change_Listener::queue_password_protected_posts()`), so the drain takes them out right after the update.
- **A change to the Indexing tab sends only what it changes, and is applied at once.** `Dirty_Tracker::is_fresh()` called every document stale when the mapping's `config_version` moved, so a save resent the whole site (58 documents on the tester's site to take one out); it now compares the document's hash only. Saving a changed mapping starts a sync, which sends what the change altered and takes out what it left out; the tab says so, or that a sync must be started when one is running. Until then a post the mapping no longer indexed, a private one for example, stayed findable until somebody synced.
- **A renamed content type is found where it is chosen.** The Indexing tab lets an admin name a type ("artikel" for posts); the documents carry that name, but the block, the shortcode, the Elementor widget, the Placement tab's "Content to search" and the type boosts named the post type, so a search restricted to posts asked for `type=post` and found nothing, and a boost for posts moved nothing. The storefront config hands the window `documentTypes` and `typeLabels` by document type, the boosts are keyed by it, and the type buttons name a renamed type by its label ("Beiträge", not "artikel"). Suggestions send the scope too (`type`, which the service will read, service request 21).
- **Every result card shows its text.** Only the `post` and `product` types had a card with text, so a page, a custom type and a renamed type showed their title alone. A card is chosen by its document type, then by the post type in its id, and is the post card for any other.
- **The category filter works on post categories.** It was given to the field named `categories` alone, so a site mapping its post categories as `kategorien` saw every subcategory under "Main categories only". It applies to every field mapped from the product or the post categories (`Index_Config::category_fields()`), with the tree and the order of its own taxonomy. And a field mapped from a hierarchical taxonomy sends the parents of the post's terms, as products do: a post under "Ratgeber › Pflege › Wolle" went as "Wolle" alone, and a filter on "Ratgeber" did not find it.
- **An AND filter counts after every pick.** The window kept a filter's counts frozen once it had a pick of its own, which is right for "any of these" and wrong for "all of these", where each pick narrows the next: it offered combinations that found nothing. The plugin keeps a copy of Searcio's `facet_match` beside the facet fields (`Facet_Config::set_match()`), the facet carries `match: 'all'`, and `mergeFieldFacets()` takes such a field's fresh counts.
- **The title, the text, the link and the image can come from a custom field**, as the docs said: each of the four menus offers "Custom field" with a meta key, and only the built-in properties that suit it (an author was offered as the link, a date as the title). An image field holding an attachment id, as ACF keeps one, is sent as its address. A post without a title is named by the first words of its text instead of "#66".
- **The synonyms field takes a second line.** The text was rebuilt from the cleaned list at every key, so Enter's new line and the space after a comma were gone at once; it is kept as typed and only the list sent to Searcio is cleaned.
- **Featured highlights on a site without a shop.** "Featured products" asked for `filter[featured]`, which Searcio refuses (422) on an index without that field, and the window showed "Current highlights" over nothing. The storefront config says `hasFeatured`, the highlights fall back to the newest without it, a row without highlights draws no heading, and the Placement tab offers "Featured" only where products carry it and says "The newest content" where there are none. The product rows section is not offered without products, and the assistant's opening lines speak of the site, not a shop (`hasProducts`).
- **A field nothing is sent for is flagged.** A field read from a protected meta key (`_interne_notiz`) is never sent, but was listed as indexed, so it was offered as a facet and a searchable field and flagged as nothing. It is left out of the list, the meta key field says that a key starting with `_` is not sent, and the searchable fields get the warning the facet and suggest fields have.
- **The Search Config tab says what is wrong in its own words.** Searcio answers in its default language (German, in an English screen) and names a field by its key ("Das Format des Feldes redirects.3.url ist ungültig."). The redirect URL, a weight, a boost and a language code get the plugin's own message, and every request sends `Accept-Language` with the screen's locale (service request 20). A redirect term entered twice, whatever its capitals and spaces, is flagged.
- **Smaller fixes.** Picking "Custom field" again in an extra field keeps its key, where it emptied it. The Sync history's search finds a run by its number or by its error (it searched nothing), and an empty table says "No sync has run yet". "Keep history for (days)" refuses a negative number (`minimum` in its schema; the settings endpoint answers a value its schema refuses with 400 instead of a server error). The classic widgets are kept out of Elementor's panel, which listed two "Searcio Search" and two "Searcio Products". Elementor's templates and floating elements, and a type the site keeps out of its own search, are not offered as content to index. "Clear cache" takes only the plugin's files out of PHP's opcode cache (`opcache_invalidate()`), not the whole server's. The assistant offers Compare only for products. On a phone, the mic and camera step aside while the field holds text, which had about 120px. The merchandising card says that a search takes the first matching rule and no other, until the service combines them (service request 16).
- Tests: `Sync_Workflow_Test`, `Document_Builder_Test`, `Index_Config_Test`, `Storefront_Facets_Test`, `Settings_Endpoint_Test`, `Sync_Endpoint_Test`, `Field_Source_Resolver_Test`, `Classic_Widgets_Test`, `Dirty_Tracker_Test`, `documentType.test.js`, `templates.test.js`, `facets.test.js`, `searchConfig.test.js`, `IndexingTab.test.js`, and the e2e `ai-assistant.spec.js`.

The second round (WooCommerce, about 430 products) and the third (Polylang, German and English) found what follows. What is the service's is in `service-requests.md` (24-30).

- **What is about products shows products.** The index holds the posts and pages too, and the highlights, the product rows, the product finder and photo search asked for every type: "The newest products" listed the site's oldest pages, a jacket's similar products were two articles, and a product finder's matches included a guide. Where products are indexed, they ask for the products' type (`productType()`), and the similar products keep to the source's own post type. The service takes no type for photo search, so its hits are kept to products in the browser (service request 26). "The newest" are not the newest yet: `/search` has no sort, so they come in the index's order (service request 24).
- **Featured highlights need the featured filter, and say so.** Searcio finds featured products through `filter[featured]`, which it refuses (422) unless `featured` is one of the facet fields, so on a shop that sends `featured` but has not added it there the row stayed empty again. `hasFeatured` now asks the facet fields, the highlights fall back to the newest without it, and the Placement tab says that the field has to be added on the Search Config tab.
- **Each page searches its own language when no language is ticked.** With the Languages section left empty, every language is indexed and each document still carries its own, but the window sent no `filter[lang]`, so the English page of a Polylang site listed the German products beside the English ones. It sends the page's language whenever the site has one (`currentLangFilter()`).
- **A page in a language the site does not index searches WordPress in that language.** The search was handed to the default language's front page (`/?s=jacket`, "Suchergebnisse für: jacket", nothing found) instead of the page's own (`/en/?s=jacket`); `siteHome` is now the front page of the page's language (`Multilingual_Support::home_url()`, `pll_home_url()` or `wpml_home_url`). Before a search the window showed the other languages' highlights and popular searches; on such a page it now asks Searcio for nothing, and shows no assistant or product finder.
- **WooCommerce's own pages are not indexed.** The cart, the checkout, the account and the shop page, and their translations, came first for "cart" and "checkout". `Document_Builder::is_shop_page()` keeps them out, the upgrade step `Unindex_Shop_Pages` takes them out of an index 1.4.0 filled (`Change_Listener::queue_shop_pages()`), and a new filter, `searcio_is_indexable`, keeps out any other post a site names.
- **Changing "Hide out of stock items" starts a sync.** The setting decides which products are visible, but saves no product, so the products it hid stayed in search until somebody synced. `Shop_Settings_Listener` starts one when it changes, where the mapping respects catalog visibility.
- **Ticking or unticking a language starts a sync.** A language added to or removed from the Languages section stayed out of the index, or in it, until somebody synced; saving it now starts one, and the tab says so. A language assigned to existing content in bulk (Polylang's setup wizard) saves no post, which the docs now say.
- **`product_type` is WooCommerce's.** A grouped and an external product were sent as `simple`; the field is now `$product->get_type()`.
- **A variable product on sale is struck through.** Its card read "from 239" with nothing to say what was taken off. The index carries the regular and the sale price of its cheapest variation, and the card strikes the regular price through beside "from".
- **Product-specific attributes can be indexed.** An attribute a product defines for itself, not one of the shop's, was never sent. A *Product-specific attributes* toggle under Product details sends those the product page shows as `custom_attributes`, each value as "Name: value". It is off by default.
- **"Only index published, visible products" is "Respect catalog visibility".** The switch decides catalog visibility alone; whether private products are indexed is the other switch's, which its name seemed to contradict.
- **"Check the endings" counts in the quiz's language.** It sends the quiz's `lang`, which the service is asked to read (service request 30).
- Tests: `Woo_Test`, `Search_Config_Endpoint_Test`, `api.test.js`, `language.test.js` and `templates.test.js`.

- **The category filter tells apart categories of one name** (search-cloud #195). lowrider.at has three "MTS Technik", under Gewindefahrwerke, Gewindefedern and Sturzdomlager. Indexed by name they were one value, `{"value":"MTS Technik","count":4103}`: ticking it filtered all three, and the tree, built name => parent by `Facet_Config::category_parents()`, placed it under whichever parent `get_terms()` returned first, so after the shop reordered its categories it showed 4K+ under a parent of 109 products.
  - Every product and every post whose mapping sends a hierarchical taxonomy as `categories` now also carries `category_paths`: each level of each of its categories from the top, joined by `" > "` (`Term_Paths::for_post()`). A `>` that stands alone in a name is written as `›`. `categories` stays as it was, for search, the assistant, the quizzes and merchandising rules.
  - Searcio reads a facet field ending in `_paths` as a tree: each path its own value, with `label` and `parent` on `/search`, all of its values rather than the 50 most frequent, and a filter on a path finding everything under it.
  - With `category_paths` among the facet fields and the filter set to a tree, `Facet_Config` hands it `tree: { depth, paths: true }`; `arrangeTree()` reads each value's parent from the value, the panel names each category by its own level (the whole path in a search within the list, which tells two of one name apart), and the filter's button, its chips and the "All filters" summary do the same. `categories` is then `hidden`, and `extractFieldFacets()` leaves it out of the window; in one list it is the other way round. The Search Config tab offers the field as "category_paths (categories as a tree)".
  - `Woo_Test`, `Document_Builder_Test`, `Storefront_Facets_Test`, `Term_Paths_Test`, `Storefront_Facet_Test`, `facets.test.js` and `FilterPanel.test.js` cover it.
- **The category filter keeps the shop's order.** The service answers by count, so the children of Fahrwerke read Gewindefahrwerke, Luftfahrwerke, Sturzdomlager, Gewindefedern, where the shop had sorted them Luftfahrwerke, Gewindefahrwerke, Gewindefedern, Sturzdomlager. A new setting, `category_filter_order` (`Enums\Category_Order`: `shop`, the default, `name` or `count`), is on the Search Config tab as *Order of the categories*. With `shop`, the facet carries `valuesOrder`, read with `get_terms()` and `orderby: menu_order`, which WooCommerce answers from the term meta its drag-and-drop writes, and walked as a tree so each main category is followed by what is under it. `sortCategoryValues()` sorts the values before the tree places them; a value the list does not have comes after the ones it does, by count.
- **WooCommerce brands are indexed.** A *Brands* toggle under Product details, on WooCommerce 9.6 or later, writes the names of a product's `product_brand` terms to `brands`, as tags are written. It is on by default for a new mapping; a saved one keeps what it had. The window names the filter "Brands".
- **A published release goes to wordpress.org by itself.** `deploy.yml` (now `deploy-to-wordpress-org`) runs the tests on the tag, checks that the tag, the plugin header and `Stable tag` are one version, that the tag is on `master` and that wordpress.org has no such version yet, and builds and checks the package. `10up/action-wordpress-plugin-deploy` (2.3.0, pinned to its commit) commits that package to SVN `trunk` and `tags/<version>`, and `.wordpress-org` to `assets/`, in one commit, and the zip it makes of what it committed is attached to the release as `searcio-<version>.zip`, with its SHA-256 in the run's summary. Run by hand from a tag it is a dry run unless told otherwise, and keeps the zip as an artifact. It needs the secrets `SVN_USERNAME` and `SVN_PASSWORD`. `Package_Test` checks that the package it built is what goes to SVN, and that the action is pinned.
- **The README's badges read their numbers from wordpress.org.** The version, the PHP, the WordPress the plugin was tested with and the rating come from the plugin's page there, so a release no longer edits them. `Version_Test` checks the badges are those.
- **Work goes to the `1.x` branch, `master` only takes releases.** Pull requests are opened against `1.x` and merged there; a release merges `1.x` into `master` and is tagged on that merge. `run-tests.yml` runs on pull requests into `master` and into every `*.x` branch, which it did only for `master`. `docs/developers.md` (**Branches**, **Releasing**, **Contributing**), the pull request template and the README say so.
- **The readme links the live demo.** `readme.txt` and `README.md` point to the demo shop at https://wordpress.demo.searcio.com/en/ and to its admin demo (`?searcio-demo-admin=en`), which opens the plugin's settings and saves nothing.

## 1.4.0

- **Every locale of the plugin's languages gets them, not English.** WordPress loads a plugin's translation for the site's exact locale and no other, so a site in "Deutsch (Sie)" (`de_DE_formal`), as fisch-gruber.at is, in Swiss German with "du" (`de_CH_informal`), in Canadian or Belgian French or in any Spanish but Spain's showed the search window, the blocks and the settings in English.
  - `languages/searcio-de_DE_formal.po` is the `de_DE` translation with the reader addressed as *Sie*, as WordPress's own formal German does: 113 strings that said *du* or used its imperative (*Prüfe*, *Wähle*, *Versuch es erneut*) say *Sie*, and the suggestion "Help me find a gift", the shopper's own words, is "Ich suche ein Geschenk".
  - WordPress's `de_CH` says *Sie* and its `de_CH_informal` *du*; the plugin's `de_CH` said *du*. It is now the formal text with ss for ß, and `de_CH_informal` is what `de_CH` was. `de_AT` stays with *du*, as WordPress's does.
  - A fallback stands the language's main locale in for one the plugin has no file for (`fr_CA` reads `fr_FR`, `es_MX` reads `es_ES`), on `load_translation_file` for PHP and `load_script_translation_file` for the scripts, only for files of its own `languages/` folder and never before a WordPress.org language pack for the exact locale. It was the plugin's own `Compatibility\Translation_Fallback` until framework 1.11.0 brought the same one (`Support\Translation_Fallback`, attached as the plugin boots), which took its place.
  - `Translation_Fallback_Test` (integration), `Translations_Test` and `Brand_Test` cover it.
- **Ctrl/Cmd+K opens the search on any keyboard layout.** `openers.js` matched `event.key === 'k'`, but a layout without Latin letters writes "ن" or "л" for that key while the browser's own Ctrl+K answers to the key itself, so the browser's search opened. `isKeyK()` takes the letter on a Latin layout (Dvorak, AZERTY) and the key (`code: 'KeyK'`) on one without. `openers.test.js` covers Persian, Russian and Dvorak.
- **A Product finder tab makes and edits the quizzes in WordPress** (search-cloud #155). `Quizzes_Endpoint` proxies `searcio/v1/quizzes` to Searcio's `/quiz-templates` with the write credentials, which never reach the browser; the list's search, filters, order and page are applied there, since Searcio returns every quiz of a site at once (fifty at most). What the editor sends is cleaned by `DTO\Quiz_Payload` (plain text, numbers for range bounds, an https picture or none, the graph's own shape), and a create is asked once, since one that timed out may have made the quiz. A 401 from Searcio reads "Connect this site to Searcio on the Connection tab first." The tab lists the quizzes in DataViews; the editor (`QuizEditor`) puts the quiz, each question and "Where the quiz ends" in a `SectionList`, offers each filter's values from `/quiz-templates/facet-values` with how many products have a value or that it is spelled in another case, picks a question's picture in the Media Library (the settings page runs `wp_enqueue_media()` for someone who may upload, and the large size of the picture picked is stored; a picture not on https, which Searcio refuses, is flagged; someone who may not upload types the address), keeps changes until "Save changes", checks the endings before publishing and asks before publishing a quiz with an ending that shows no products, shows each reason Searcio gave for a refusal, and asks before leaving with unsaved changes. Its graph rules (`quizEditor.js`) are the Searcio panel's. `Quizzes_Endpoint_Test`, `quizEditor.test.js` and `quizzes-tab.spec.js` cover it, and every string is translated in the seven locales.
- **The search window opens under WordPress's toolbar.** A logged-in user sees the toolbar over the page, and a theme may lift it above anything a window can be: fisch-gruber.at gives it `z-index: 2147483647`, so the window's search field was under it. `adminBarOffset()` (`src/utils/adminBar.js`) measures where the toolbar ends, and the search window sets it on `body` as `--whsc-admin-bar` as it opens and when the screen changes size: the overlays of the window and of its sheets start there, and the window's height leaves it out. It is measured, not assumed, since the toolbar is 32px tall on a desktop, 46px up to 782px and scrolls away with the page below 601px; for a visitor it is 0. `adminBar.test.js` covers the measure and `admin-bar.spec.js` the window under a toolbar lifted that high, on a desktop and on a phone.
- **The assistant's reply is shown as it is written.** `streamAssistant()` reads `POST /assistant/stream` (search-cloud #153) with `fetch` and a stream reader, not `EventSource`, which cannot POST: the products are drawn on `products` (the whole list so far each time), the reply grows on `delta`, and `done` carries the turn kept in the history. A refusal still comes before the stream with the statuses of `POST /assistant`; a service without the endpoint (404), a browser without `TextDecoder` or an answer that is not `text/event-stream` is answered by `askAssistant()`. A turn that fails part-way leaves the thread, so "Try again" adds no second copy. "Thinking" shows until the first words arrive. `api.test.js` (chunks cut inside a line, the 404 fallback, a refusal, an `error` event, a cut stream, a plain JSON answer, the language) and `ai-assistant.spec.js` (the mock streams with `assistantStream`) cover it.
- **The page's language goes with every request that takes one.** `filter[lang]` on `GET /quizzes` (search-cloud #148), `GET /search/popular` (#151) and `POST /search/visual` (#152), and `filter: { lang }` in the body of an assistant message (#149), on a multilingual site only; a service from before ignores them. `api.test.js` covers each, and that a single-language site sends none.
- **The assistant types its reply out.** The service streams the reply in pieces of a phrase or a sentence, and drawn as they came each piece appeared at once. `useTypewriter()` (`src/utils/typewriter.js`) types what has arrived out frame by frame, a word at a time and a tenth of what is still to type while it is behind, so a long backlog is on screen within a second and never cut inside a word or a Markdown mark; a caret blinks at the end of the reply while it is still arriving or being typed (`.is-writing`). A reply typed out once is drawn whole when it is drawn again, and a visitor who asks for less motion gets it whole and a caret that does not blink. On the demo shop a 693-character reply was typed out over 1.5 seconds. `typewriter.test.js` covers the steps and the hook.
- **A filter value with a comma is sent whole.** `/search` read `filter[categories]=Jacken, Mäntel & Strick` as two categories that do not exist. `filterValue()` (`facets.js`) keeps the comma form, which every service reads, while no value holds a comma, and otherwise sends the values as a list, `filter[field][]=` once per value (search-cloud #145). The facet bar, the quiz's answers (`applyOption()`, each tag one whole value) and the category row of `ProductList` go through it. `facets.test.js`, `quiz.test.js` and `api.test.js` cover it.
- **A merchandising rule can be kept to one language.** On a multilingual site each rule on the Search Config tab has a Language select ("Every language" or one of the site's languages), sent as `lang` (search-cloud #147); a German rule "jacke" fired on the English search "jacket". `searchConfig.test.js` covers it.
- **The settings tabs open without waiting for Searcio.** Each tab asked the server for what it showed every time it was opened, and those reads went on to Searcio: on the demo shop a tab took 2.5 to 14 seconds, and the connection's status was asked from three tabs. `Search_Cloud_Client` keeps the reads the settings screen makes in transients (`health()` five minutes; `get_search_config()`, `list_quizzes()` and `quiz_facet_values()` ten), named after the write key so that keys entered anew read afresh, keeps only successful answers, and forgets what a change changes (`update_search_config()`, the quiz writes, `connect()`, `disconnect()`). Site Health and the daily sync ask with `fresh`, and so does "Test connection" (`POST /connection/test` takes `fresh`). In the browser, `src/admin/settings/remote.js` keeps what a tab read for the visit (five minutes at most), shares one request between parts of the screen that ask the same, and forgets it on a save; the Sync tab's status stays live. On the demo shop a tab opened again showed in 150 ms with no request. `Search_Cloud_Client_Test` and `remote.test.js` cover it.
- **Searcio is told the shop's currency.** `Woo::currency()` is WooCommerce's ISO 4217 code; the Search Config tab's save adds it to `PUT /search-config`, and the daily job sends it alone, so a shop that never saves the tab is told within a day (search-cloud #149). The assistant wrote dollars on a euro shop. `Search_Config_Endpoint_Test` and `Shop_Currency_Test` cover it, with and without WooCommerce.
- **Search as you type starts sooner.** The service answers a live search lexically at once since search-cloud #143 (200-250 ms, the server's share 30-70 ms), so the pause before one is most of the wait: `LIVE_SEARCH_DEBOUNCE` is 150 ms (was 300) and `SUGGEST_DEBOUNCE` 120 ms (was 200).
- **The search window opens faster.** Measured on the demo shop, the service's answers aside, the plugin's own share of a search was already small: a request leaves 1 ms after Enter and the results are drawn 45-50 ms after the answer. What was left to win was around it.
  - Every `/search` asks for `highlight=0` (search-cloud #164): the window never shows a hit's highlighted fragments, and highlighting was about 40% of the engine's time on the demo shop's index.
  - The page opens the connection to the service before the first search, so it does not wait for DNS, TCP and TLS (100-300 ms on a real network): `Frontend\Resource_Hints` adds `<link rel="preconnect" crossorigin>` to the head when the storefront script is already enqueued then (a placement on every page, a block theme's templates), and `preconnect()` adds the same link as the script boots, for a block a classic theme draws after the head. `crossorigin`, since the requests omit credentials.
  - What the window shows before the visitor types - the storefront config, card templates, popular searches, quizzes, and the highlights (now kept 5 minutes) - is kept in `sessionStorage` under its TTL, so on the next pages of the visit the window opens full: 157 ms and no request on the demo, against 2.5 s on its first page. Two callers that ask for one of those at the same time share a request, and a caller that stops waiting does not cancel it for the other.
  - `warmUp()` asks for the storefront config, the popular searches and the highlights row of the control (its scope and highlights source, built by the same `fetchHighlights()` the window uses, so the two share one request) as the pointer reaches a search control, it takes focus or a finger touches it (search-cloud #164). On the demo all three left at the hover, about 400 ms before the click, and the first card was drawn 80 ms after the highlights arrived.
  - A result card is at most about 260px wide, and its image was WordPress's 1024px size: `Field_Source_Resolver` sends the 768px size (`medium_large`), about half the weight. A sync sends the products again with it, since their image changed.
  - `api.test.js` covers the kept answers across pages, the shared request, a missing `sessionStorage`, `warmUp()` with the highlights of its control, `highlight=0` and `preconnect()`; `Resource_Hints_Test` the hint in the head; `Field_Source_Resolver_Test` the image size.
  - The readme's *External services* says it: on a page that shows the search, the visitor's browser connects to Searcio as the page loads and asks for the window's settings, the popular searches and the products it opens on as the pointer reaches the search, before any search term is sent.
- **The product finder follows answers that ask for words or a price range.** A quiz answer's `keywords` is one more word group, sent as `keywords[n]=` (every group must match; comma-separated alternatives within one), and its `ranges_matched` merge by field like tags and go out as `range[field]=min:max`, as the service's widget contract describes (`docs/api/quiz.md`). Answers that differed only by words showed the same broad results: on schluesselbaer.at "Fenster", "Tür" and "Vorhangschloss" each showed the same 35 products. `quiz.test.js` and `api.test.js` cover it.
- **Photo search, similar products and the assistant's products keep to the page's language.** None of the three takes a language filter, so on a multilingual shop they answered in every language: the similar products of the English rain jacket on the demo shop opened with the same jacket in German. `fetchSimilar()`, `visualSearch()` and `askAssistant()` keep the hits in the page's language and those without one (`language.js`, `inLanguage()`), on a site with a language filter only, and the similar products ask for one row per language (at most 20, the service's limit) so the row still fills. `api.test.js` and `language.test.js` cover it.
- **An assistant reply's numbered list keeps counting.** Models write a blank line between numbered items; the renderer closed the list there, so each product read "1.". A blank line now ends a paragraph and not a list, and an ordered list a paragraph interrupts carries on from the number its first item was written with (`start`). `markdown.test.js` covers it.
- **Text on either side of a block stays two words in the index.** `Field_Source_Resolver` stripped tags with nothing in their place, so `<li>Wool</li><li>Silk</li>` was indexed as "WoolSilk", and a heading ran into the paragraph before it ("list.Road", which a search tokenizer keeps as one word). A line break, a rule and the start or end of a block-level element now leave a space (`WORD_BREAK`), runs of spaces become one, and the derived excerpt leaves out shortcodes and the blocks the content leaves out. The daily full sync re-sends what is already indexed. `Field_Source_Resolver_Test` covers it.

It was a notice of the WordPress components package, and looked like whichever version of that package the plugin was built with: a bar with a red edge in 1.1.0, a bordered box with the current one.
- **A sync that meets a failure no longer stays paused until somebody resumes it.** When Search Cloud did not take a batch - it was down, or the connection dropped - the sync was set to *Paused* with a message saying it would retry, and then nothing retried it: only a click on *Resume* did. Until that click no scheduled sync started, and no change made in the shop was sent either, because changes wait for a running sync to finish. That is how a price or a stock level could be right in the shop and wrong in the search for days. The sync now stays *Running*, says when it tries again, and sends the same batch after 1, 2, 5, 10, 15 and 30 minutes. If Search Cloud is still not answering after that hour it ends as *Failed*, which frees the way for the changes and for the next scheduled sync.
- The daily scheduled sync continues a paused sync instead of doing nothing because of it. That brings back a sync an earlier version left paused, within a day of updating, and it means a pause made by hand lasts until the next scheduled sync at the latest. The Sync tab says so while a sync is paused.
- A batch that is sent again is counted once. Each try used to add its posts to *Processed* and its documents to *Failed*, so a sync that got through in the end could report more processed than there was to process.
- The WP-CLI command `sync run` waits and tries again as the background sync does, and exits with an error when the sync did not complete. It used to print *Sync completed* for a sync that had failed.
- The search box's placeholder follows the colour of the box's text, so it stays readable in a box set light on dark.
- The storefront script starts through `wp-dom-ready`, and its handle is named after the plugin's slug.
- REST routes say what each parameter is, so a value of the wrong shape is refused with a 400 before any code runs.
- The package no longer carries the framework's private updater or its command runner, neither of which this plugin uses.
- The JavaScript unit suite runs through `wp-scripts test-unit-jest`: `@wordpress/scripts` 36 moved `test-unit-js` to Vitest and stopped bundling Jest.

An earlier sync and onboarding flow kept its progress in standalone options - a discovery counter and status, initial-sync flags, several "last run" timestamps and a sync interval - which nothing has read since the current engine moved all of it into the sync-runs table. They lingered in the options table, where a value like a discovery status still reading "running" looks like live state. The opt-in "delete my data" uninstall path clears them too, for sites removed without ever reactivating.
- The Search Config tab now covers the whole of Search Cloud's search configuration. Merchandising rules (pin products to the top of a search, keep products out, show a banner) and the three site-level switches - AI search with its index status, AI visual tagging, and ranking by what visitors click - were only editable in the Search Cloud panel; the API exposes them now, so they are editable here too. A switch your plan does not include is shown but disabled, with the reason.
- Fixed click-through tracking never recording anything. The beacon sent a JSON body, which is not a CORS-safelisted content type, so the browser had to preflight it - and the API answers preflight requests without any CORS headers, so every click was blocked before it left the page. The beacon is now form-encoded, which needs no preflight and which the API reads identically.
- Fixed a sync that could stop dead with no way back: the follow-up worker tick was only scheduled at the very end of a tick, so a tick killed part-way through (a slow API against PHP's `max_execution_time`, an out-of-memory, a restarted worker) left the run on "Running" with nothing left to advance it - and because a run in that state holds the single active slot, every later scheduled sync silently did nothing. A tick now arms its successor before it starts working, and the scheduled sync revives a run whose worker has died instead of skipping it.
- Ticks are now time-boxed (20 seconds by default, filterable with `searcio_sync_tick_budget`) rather than bounded only by a batch count. Removing stale documents costs one request each, so a large clean-up could previously run hundreds of blocking requests in a single tick and be killed part-way through.
- Documents the index refuses to delete are now counted and reported on the sync run instead of being dropped from the queue in silence - a failing delete endpoint used to look exactly like a healthy clean-up, with "deleted 0" and no explanation.
- Incremental syncs now say why they failed. A failed incremental run was written to the history with no reason at all, and a rejected push that wasn't a plan-limit recorded nothing whatsoever, so the dashboard showed either an unexplained failure or no sign of a problem at all.
- Removed the leftover site ID option on upgrade. Nothing has read it since the connection moved to key-relative endpoints - the connection screen reads the id straight from the API - so all it did was go quietly stale and mislead anyone inspecting the options table (one site still held `5` while the API reported `4`).
- Fixed sync history retention never deleting anything: the purge built a comparison query the database layer then rejected, so the runs table grew without bound however the retention setting was configured.

## 1.0.2

- Security: hardened the server-designed result card renderer so a value from an indexed document can no longer break out of an HTML attribute or smuggle a `javascript:`/`data:` URL into a link. Field values are now fully escaped (quotes included) and script-bearing URL schemes are stripped before the card markup reaches the page.
- Security: the public domain-ownership `verify` endpoint now requires the verification token the Search Cloud ping always sends, so a tokenless request can no longer read the write key.
- Security: WordPress protected meta (keys starting with `_`) is no longer pushed to Search Cloud through a `meta:` field mapping by default, so an over-broad mapping can't leak internal data into public search. Opt a specific key back in with the new `searcio_index_allow_protected_meta` filter.

## 1.0.1

- Fixed a sync that could stay stuck on "Running" when its background worker stopped (WP-Cron disabled, no site traffic, or a tick killed mid-run). Pause, resume, and cancel now detect a dead worker and act on the run directly instead of parking a control signal no live tick will ever read; cancelling also clears any stray scheduled tick and frees the active slot so a new sync can start.
- Added a wp-env integration test suite (activation, the sync REST endpoint, and the full start/tick/complete and dead-worker recovery workflows) alongside the existing unit tests.
