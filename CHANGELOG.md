# Changelog

## 1.2.1

- **The words of the settings screen's header stay once they are there.** The title and the description fade in word by word, and a frame after a word had arrived it was gone for one frame and back, which read as a flicker. The animation library ends a fade by taking the animation away and writing its last value as a style, and the release in the bundle did the two a frame apart. `motion` asks for a release that does not. The bundle held the one `@wordpress/components` brings instead, because the build read the top of `node_modules` only, and nothing said so: the build passed and `npm ls` was right. The build now gives a package the dependency npm installed for it, and bundles nothing from outside the plugin. Only the script of the settings screen changes, by about 14 KB; the storefront's script and every stylesheet are the same byte for byte. A new end-to-end test reads each word in the first task after its fade ends, with the animations the suite otherwise turns off.
- Updated the webhead plugin framework to 1.4.1, which brings the build's new way of finding a package. Three packages of the build tooling are raised for advisories: `postcss-selector-parser`, `katex` and `smol-toml`. `npm audit` still reports `braces` and `sprintf-js`, which have no fixed release, and `simple-git` with its argument parser, whose fix the wp-env the tests start with cannot run on. None of them is in what the plugin ships.
- **Numbers and dates on the settings screen follow the language of the screen, not of the browser.** The plan allowances and the connected notice on the Connection tab, the counters of a running sync and the sync history were written with the browser's own formatting, so a browser set to another language than the WordPress profile mixed the two: an English screen in a Persian browser read "۲۷۰٬۰۰۰ of ۳۰۰٬۰۰۰", and a date in the history came out in the Persian calendar. A number is now grouped as the language of the screen groups it, with the digits WordPress itself writes in every language. A date in the sync history is written as the rest of wp-admin writes one: in the site's date format and time zone, where it used to be the browser's time zone, with the month in the language of the screen. The end-to-end suite pins its browser to `en-US`, the one setting that could not show this, so two specs now run in a Persian browser.
- **The Disconnect confirmation says what disconnecting does.** It said that only the saved credentials are removed and that nothing in the Search Cloud account changes, while disconnecting has Search Cloud delete the site and its search index. It now says so, that the storefront falls back to WordPress's own search until the site is connected and synced again, and that nothing in WordPress is deleted, and the button that goes ahead reads *Disconnect and delete the index*.
- *How connecting works* names the link for another email address by its label, *Not this email?*. It pointed to a "Use a different email" that the tab does not have.
- The Terms of Service, Privacy Policy and Data Processing Agreement links on the Connection tab fall back to the documents at `https://searcio.com`. The three were left at `webhead.dev` when the service moved, where they ask for a password. Search Cloud supplies its own links, so the old ones showed only until those arrived, and for as long as the service could not be reached. The unit suite now checks that the three are at the address of the service.
- The readme says what connecting sends to Search Cloud - the site's name and address and the email address and name of the admin who connects - and what saving the Search Config tab sends. Its installation steps describe connecting with one click, and it lists the AI Assistant among the features.
- The README's badges show the current version and the WordPress and PHP the plugin asks for, and the unit suite now compares the version wherever it is written, so they cannot fall behind again. The documents describe connecting, disconnecting and the capabilities as they are, list the connection routes, and call the quiz tab by its name, *Product finder*.

## 1.2.0

- **WordPress 6.8 is now the minimum**, up from 6.0. It is the version the framework is built and tested for, and the header had been promising more than the plugin delivered: the settings screen has needed 6.2 since it moved to React 18, and is written against the components of a current WordPress. A site on an older release keeps the version it has and is not offered this one.
- **A page without search costs nothing.** The plugin boots on every request, and on a page with no search trigger it used to send a database query and translate eleven strings before deciding it had nothing to do. It now sends no query and loads no translation there: the storefront script and what it is given are only prepared by a block or a widget that is actually on the page.
- **The settings screen is redrawn on the framework's page shell.** The page has one title and each tab one heading under it, the tab strip runs the width of the screen and scrolls on a phone instead of wrapping, and the cards, fields, notices and placeholders are the WordPress Design System's own. Black is the brand and green marks focus and links. *Upgrade plan* is an action in the page header like any other, and no longer purple.
- A screen that could not load now says why and offers to try again. The settings, the Indexing tab and the Search Config tab each waited on a request, and when one failed the Search Config tab stayed a placeholder for good while the others showed an empty screen.
- A save that fails is reported beside the button that failed, with the reason the REST API gave. The General tab used to open a dialog that said to review the fields whatever had gone wrong, and the other tabs a toast that disappeared. Search Config, which saves two things with one button, says what was stored and what was not in one message.
- Clearing the sync history, deleting a run from it and disconnecting from Search Cloud ask first. None of the three can be undone by a click, and the first two used to happen at once.
- The consent checkboxes on the Connection tab list their documents as links under the sentence they belong to, and *Learn more* is *How connecting works*, beside *Not this email?*.
- The plan allowances on the Connection tab are three colours again - fine, close to the limit, spent - and a redirect in Search Config stacks its two fields on a phone instead of squeezing them into one row.
- The search and products blocks space the controls in their editor panels evenly. Fields had been touching whatever followed them since the panels moved to the design system's controls.
- Updated the webhead plugin framework to 1.4.0, with the WordPress packages the admin is built on. `npm audit` reports only `braces`, which has no fixed release.
- The Elementor widgets are listed in the editor panel under *webhead Search Cloud* rather than under *General*. Widgets already on a page are unaffected: they are saved under the same names.
- The storefront adopts the framework's new reset, which keeps WordPress's own controls looking the same on every site. The search modal has a design of its own, so its stylesheet is written to outrank the reset, and the Elementor style controls to outrank both. Theming through the `--whsc-*` properties is unchanged; a rule of your own that restyles a `.whsc-*` element directly now needs `!important` to win.
- **The search looks the same on a site that styles every element.** Most sites style the whole page - an Elementor kit's Site Settings for buttons, form fields, links, headings and images, a theme's `h3 {}` and `a:hover {}`, a designer's own CSS behind an id - and the modal is drawn in `body`, under all of it. A customized kit used to reach deep into it: its button colours and padding on the chips and the filters, its field border on the search field, its link colour on the cards, its heading type on the section titles. Every element the plugin draws, its icons and its placeholders are now taken off the site's rules before the plugin's own are applied, in every state, hover and keyboard focus included. The site's own type - the font, its size, the colour of the text - is still followed, as before. A new end-to-end test customizes the kit and the site's CSS and compares the storefront element by element with the plain site.
- **Cards designed in Search Cloud are drawn again.** A placement set to the *Search Cloud* card design has shown an empty modal since 1.0.2: the step that strips script-bearing links from a template asked the browser for a selector no browser accepts, and the error took the modal down with it. It went unnoticed because the unit tests read the markup through a parser that accepts that selector. The check now reads each element's attributes instead, which also covers the link of an inline SVG that the selector could not have matched.
- **A designed card comes out as it was drawn in the panel.** The plugin's own card frame no longer goes round it - the template draws one, and the result was a card inside a card. A site's rules for headings, links and images no longer reach the template's elements. What a template leaves unsaid starts where the panel's canvas starts: no margins, a heading and a link in the type and colour of what holds them, a list without bullets. And the template's stylesheet, written with one class per element, now outranks the site's rules and the plugin's, so what a template says, it gets.
- **The carousel works in a right-to-left page.** Its track starts at the right edge there and scrolls into negative positions, which the script read as if it were the left: the previous arrow never came alive, the next one pushed against the edge and moved nothing, a dot did not go to its page and none was ever marked as the current one. Positions are now counted from the start of the track in either direction, the arrows point the way they move, and an arrow key moves the track the way the arrow points.
- Keyboard focus is drawn whole. The ring round a filter chip lost its top and bottom to the row it sits in, which scrolls; the first card of a carousel lost the left side of its ring, and the cards and the *Compare* switch at the edge of the assistant's results lost theirs the same way. The filter row now leaves room for the ring, and the others draw it inside. A product in the compare table has the surface's ring instead of the browser's, the search box trigger shows focus as a ring in the placement's accent round the whole box, *Clear all* and a price filter's *Clear* show one too, and every ring is the same width on a dense screen.
- **The arrow keys move through the search suggestions.** The list told a screen reader it was a list to pick from, and then could only be walked with Tab, one stop per suggestion. Down and Up now move through it, and round from one end to the other, while the cursor stays in the search field; Enter searches for the suggestion the keys are on, and for what was typed when they are on none. Typing on forgets the mark, and Down brings back a list that Escape put away. The suggestion the keys are on carries a ring, as one reached with Tab now does: the faint fill it had was the pointer's mark and hard to see.
- **A link in an assistant's reply is a link.** A reply that named a page read `The [size guide](https://…) helps` on screen, brackets and address and all. It is drawn as a link now: a page of the shop opens in place, as a result card does, and another site opens beside the shop. The model writes the address, so only an `http(s)` address or a path on the site becomes a link; anything else - `javascript:`, a `//host` or `/\host` address dressed as a path - stays the words it was the label of. Search redirects are held to the same rule, which now also refuses `/\host`.
- The message the search shows when a search or a photo search fails is the surface's own tinted block, the one the assistant and the product finder show. It was a notice of the WordPress components package, and looked like whichever version of that package the plugin was built with: a bar with a red edge in 1.1.0, a bordered box with the current one.
- **A sync that meets a failure no longer stays paused until somebody resumes it.** When Search Cloud did not take a batch - it was down, or the connection dropped - the sync was set to *Paused* with a message saying it would retry, and then nothing retried it: only a click on *Resume* did. Until that click no scheduled sync started, and no change made in the shop was sent either, because changes wait for a running sync to finish. That is how a price or a stock level could be right in the shop and wrong in the search for days. The sync now stays *Running*, says when it tries again, and sends the same batch after 1, 2, 5, 10, 15 and 30 minutes. If Search Cloud is still not answering after that hour it ends as *Failed*, which frees the way for the changes and for the next scheduled sync.
- The daily scheduled sync continues a paused sync instead of doing nothing because of it. That brings back a sync an earlier version left paused, within a day of updating, and it means a pause made by hand lasts until the next scheduled sync at the latest. The Sync tab says so while a sync is paused.
- A batch that is sent again is counted once. Each try used to add its posts to *Processed* and its documents to *Failed*, so a sync that got through in the end could report more processed than there was to process.
- `wp webhead-search-cloud sync run` waits and tries again as the background sync does, and exits with an error when the sync did not complete. It used to print *Sync completed* for a sync that had failed.
- The search box's placeholder follows the colour of the box's text, so it stays readable in a box set light on dark.
- The storefront script starts through `wp-dom-ready`, and its handle is `webhead-search-cloud-bundle-search`.
- REST routes say what each parameter is, so a value of the wrong shape is refused with a 400 before any code runs.
- The package no longer carries the framework's private updater or its command runner, neither of which this plugin uses.
- The JavaScript unit suite runs through `wp-scripts test-unit-jest`: `@wordpress/scripts` 36 moved `test-unit-js` to Vitest and stopped bundling Jest.

## 1.1.0

- **Search by photo.** A shopper can upload a photo (or take one, on a phone) instead of typing: a vision model describes what it sees and searches for that. The camera button only appears when the site has the feature turned on, and the tags the model read are shown above the results, so an unexpected result set reads as a misread photo rather than as broken search. A rejected image, a spent monthly allowance and a feature that has since been switched off each say what happened instead of failing silently.
- **A guided quiz.** A new tab walks a shopper through a few questions and turns their answers into a filtered search — for the customer who knows what they want but not what it is called. The whole question graph arrives in one request, so every step after the first is instant and the network is only touched again at the end. Answers can be changed with Back, the quiz can be restarted, and what was answered is listed beside the matches so a thin result set is explainable. The tab appears once at least one quiz is published in the Search Cloud panel.
- **Similar products.** A "you may also like" row driven by the product's own meaning rather than by shared tags, from `GET /search/similar`. Similarity is semantic, so a site without AI search answers with an empty list and the row simply does not appear - as it does when a request fails. A recommendations row that leaves an empty box behind is worse than no row.
- **Category merchandising now reaches the storefront.** The rules were already editable here, but nothing on a category page ever ran a Search Cloud search, so a rule with a category trigger could never fire: it only applies to a request carrying `filter[field]=value`. A new block and Elementor widget render that listing - pinned products first, hidden ones gone, the rule's banner above it. Placed on a template, it resolves the category (or the product, for the similar row) from the page, so it is placed once rather than per category and per product.
- **A product is indexed under its parent categories too.** A product is usually filed under its most specific category only, and only that category reached the index - so on a store whose shoes sit in "Boots", "Sandals" and "Sneakers", a filter on "Shoes" matched nothing, and neither did a quiz answer or a merchandising rule naming it. Each product now carries every ancestor of its categories as well, each name once - what WooCommerce's own "Shoes" archive already lists - so a category listing placed on a parent category shows its children's products. A custom field mapped from a taxonomy still sends only the terms the item is assigned.
- Fixed category, tag and attribute names showing HTML entities, as in "Vergaser &amp; Ansaugung" on a facet chip and in the compare table. WordPress stores a term name escaped and it was indexed as stored; names are now sent as they were typed. That also fixes a category listing on any category with "&" in its name, which asked for the typed name and so could never match.
- Renaming, moving or deleting a category now updates the products in it. None of those saves a product, so the index kept the old name - or the old parents - until something else touched each one. The products filed under the category or under any of its children are queued like an edit; changing only the description or the slug queues nothing.
- Products already in the index pick up the parent categories and the decoded names on the next sync, scheduled or started by hand. The documents changed, so a normal sync re-sends them; no forced re-sync is needed.
- **Security: the domain-verification endpoint no longer hands the write key to anyone who asks.** `/wp-json/search-cloud/v1/verify` exists for one caller - Search Cloud's ownership ping - which carries a token computed from the service's own application key, so no plugin can ever check it. Requiring the parameter proved nothing: appending `?token=x` returned the site's write key to any unauthenticated request. That ping is dispatched once, minutes after a connection attempt, and never repeated, so the route now answers only while a connection this site started is still expecting it, and is closed the rest of the time.
- Fixed the assistant breaking permanently after a long reply. Each turn sent back as history is validated separately and capped at 4,000 characters, so a reply over that length made every following message fail - and because the reply stayed in the thread, no retry could clear it. History entries are trimmed to the cap and empty ones dropped.
- Fixed a failed keystroke throwing the shopper off the page. In search-as-you-type mode a single rate-limit or server error mid-word navigated them to WordPress's own search with half a word as the query. Handing over to native search is right for a search someone asked for, not for a keystroke; a live search that fails now just shows the notice.
- Fixed a similar-products row set above 20 items disappearing instead of rendering: that endpoint caps `limit` at 20, while the control allowed 24. The cap now follows whichever endpoint the row actually calls.
- Fixed saving Search Config deleting ranking boosts for any content type this site does not index. The section is replaced wholesale on save, and the list was rebuilt from local post types alone - so a boost set in the panel for a type living elsewhere was silently dropped. Those are now passed through untouched.
- Fixed a switch left on after a plan downgrade rejecting every unrelated Search Config save. Re-enabling a feature the plan no longer includes is a validation error on that field, and the tab re-sends its whole state on every save. Turning one off is always allowed, so it is now sent as off rather than as a doomed on.
- **Search Config only suggests fields your documents actually have.** The suggestions were a list kept by hand in the tab, and it had drifted from the indexer: it offered `tags`, which is written as `product_tags`, and left out `in_stock`, `on_sale`, `product_type`, `skus`, a variable product's `price_min` and `price_max`, and every product attribute (`attr_{name}`). The API accepts any field name, so a facet on one that no document carries is saved without complaint and stays empty - which is how a facet on `category` (the field is `categories`) left a category facet with nothing in it, and a quiz filtering on it with no results. The list now comes from the indexer: the same code that decides which fields a document is written with reports them for the saved Indexing mapping, so a field is offered exactly when a document can have it. A configured facet or suggest field that no document from this site has is now flagged under the field, and the merchandising rule's filter field offers the same list; its example read "category" as well.
- Fixed a half-written search redirect being sent and then silently vanishing: the API drops a rule missing either the term or the destination rather than rejecting it, so the row disappeared on the next read with nothing to explain it.
- Fixed a newly added merchandising rule showing a deleted rule's category trigger, because the new row was created without those two fields.
- **Fixed "Search results only" products never reaching the search index, while "Shop only" products did.** With "Only index published, visible products" on - the default - indexing asked WooCommerce whether a product is visible, and WooCommerce answers that for the page being served: "Search results only" counts only on a search results page, "Shop only" everywhere else. A sync runs from WP-Cron, WP-CLI or REST, never on a search page, so the answer was exactly backwards. A product is now indexed when WooCommerce's own search would list it: "Shop and search results" or "Search results only", and not an out-of-stock product the store hides from its catalog. The `woocommerce_product_is_visible` filter still applies, so an extension that hides products keeps them out of search too. A private product now follows the content type's private option alone; WooCommerce's check also asked whether the current user could edit it, and a sync almost never runs as one, so private products were effectively never indexed. No forced re-sync is needed: search-only products were never sent, so the next sync pushes them, and it removes the shop-only products the previous full sync indexed. A shop-only product first indexed by an edit since that sync is not in its list, so it leaves the index the next time it is saved - a forced re-sync would not remove it either.
- **Filter by price.** A numeric field configured as a facet - price above all, but rating and review count work the same - now gets a minimum and a maximum instead of chips. Chips were never usable here: facets are exact values, so a price field would have offered one chip per price, and because a number is indexed as a number it has no keyword form to aggregate at all, which is why such a field showed a heading with nothing under it. The bounds are sent as the API's `range[]` filter, either side can be left open, and the span of the results on screen is offered as a hint rather than as a cap.
- **The results are no longer one page deep.** The search API pages, and the modal only ever asked for the first page - so on any catalogue with more than twenty matches the rest were unreachable. A Load more button now appends the next page until the last one comes back short. The heading says how many results were matched where the service can say - a search without semantic ranking, and the quiz, which always searches without a term - and how many are on screen where it cannot: a semantic query's reported total counts the window the engine retrieved rather than the matches, and climbs as you page (23, then 40, then 60 on a 96-document index), so presenting it as a result count would be wrong in both directions.
- **Plan allowances are visible in wp-admin.** The connection health check has always returned every metered allowance - searches, indexed documents, AI messages, photo searches, image tagging - and the plugin kept only the document count. A store could spend its monthly searches, have its storefront quietly fall back to WordPress search, and find nothing anywhere in wp-admin saying why. The Connection tab now shows each allowance, with the ones near or past their limit marked.
- Clicks on quiz results and on a curated category listing now count towards click-ranking. Both come from a real search that returns an attribution id, and it was being thrown away.
- **Search-term redirects.** A search for a term you have configured now sends the visitor straight to a page instead of showing results. Deliberate searches only: in search-as-you-type mode a redirect never fires part-way through a longer query, so typing "sale shoes" on a site that redirects "sale" no longer throws the visitor off the page mid-word. Rules are editable in Search Config, and a destination that is not a plain http(s) or same-site link is refused before the browser is sent anywhere.
- **Merchandising rules can now curate a category page**, not just a typed search: give a rule a filter field and value (e.g. `category` / `shoes`) and it fires on that listing instead. Existing rules are unaffected.
- **A merchandising banner now actually appears.** The Search Config tab has always let you attach one to a search, but nothing on the storefront ever rendered it, so the field looked broken. It shows above the results, and is themeable like the rest.
- The photo button and the quiz are themeable from the block editor and Elementor like every other part of the widget — colours, hover states and radius. Left alone they follow the colours already set for the modal.
- Fixed most of the Elementor widget's typography controls doing nothing. The result card's title, price and price suffix, the section titles, popular searches and the search field all kept the storefront stylesheet's own size, weight and line height, because that stylesheet is written at a higher specificity than the rules Elementor generates; the search-box trigger lost its letter case the same way, and a site's Elementor Kit styles for inputs could override the search field as well. Every typography and border control on the widget now outranks both, and the price typography reaches the amount itself, which set its own weight.
- The search service moved from `search.webhead.dev` to `https://searcio.com`. The address lives in a single constant, so every request the plugin makes - server-side syncing and the search, assistant and click tracking a visitor's browser sends - follows it. The wordpress.org external-services disclosure and the docs name the new address. Nothing is stored per host, so existing keys keep working and no rebuild of the JavaScript is needed.
- **Security: the write key and write secret are no longer sent to the browser.** They were marked `masked`, but that only changes how the field is drawn - the settings response still carried the stored value, encrypted, to every user who could open the settings screen, including one granted nothing beyond the view capability. The screen only ever needs to know whether a key is saved, so that is all it is now told; the credentials can still be written through the same endpoint, and are never read back.
- Fixed "leave blank to keep it" erasing the saved key. Typing into the write key or secret field and deleting it again sent an empty value that replaced the stored credential. An empty or untouched credential is now left as it is; disconnecting still clears them.
- Updated the webhead plugin framework to 1.3.0, and with it the WordPress packages the admin is built on to their current majors. `npm audit` reports nothing.
- **The search modal can be styled in Elementor while you look at it.** The modal is closed until a visitor opens it, and clicking the trigger in the editor only selects the widget, so every Style setting below the trigger was changed blind. *Keep open while editing* (Content → Modal) opens it in the editor preview, and *Preview search* runs a search there so result cards, filters and prices are on screen to style. Visitors never see it open by itself - the server only asks for it while rendering in the editor - and a preview search is nobody's search: it is not saved as a recent search, and a term set up as a redirect does not navigate the editor away.
- **The Elementor widget's settings are where you would look for them.** One long *Search* section of content settings is now *Trigger*, *Search*, *Results* and *Modal*. The mode tabs sat under *AI Assistant* though they sit above every mode - they are *Mode tabs* now. The section title style, used by every heading in the modal, moved from *Recent & popular* to *Modal*. *Type filters* styles every filter group, so it is *Filters*, and the *Search button* colours also paint Load more and Apply, so they are *Primary buttons*. Saved widgets keep every value.
- **New Elementor settings for matching a theme:** the overlay colour; one font family for the whole modal; the content width inside the full-width modal; the card image's aspect ratio, fit, background and radius; the sale badge's colours and radius; the carousel's card width per device and its arrows' size, radius, shadow and hover colours; each filter group's name; typography for the mode tabs, the primary buttons and suggestion items; and the trigger's alignment and the search box's width. For a different layout, the modal can also be a narrower dialog centred and set down from the top (with its top corners rounded too), a card title can keep one to five lines before its ellipsis, and the stock line can be hidden.
- Fixed the modal overlay never fading in. Its rule was scoped under the element the plugin mounts into, but the overlay is placed straight into the page body, so the rule - and now the overlay colour setting - never reached it.
- Fixed the carousel counting its pages for a narrower track than it had. It recounted on window resizes only, and the track also changes width when the popular searches column appears beside it or the layout switches at a breakpoint; after a device switch in the Elementor preview it showed 23 dots for 7 pages.
- Updated the webhead plugin framework to 1.3.1. Its shared frontend reset took the keyboard focus ring away from every tab on the storefront and put nothing in its place; it now draws one. The search modal's tabs, filter chips and carousel dots already drew their own ring in the placement's accent and keep it, so nothing changes on screen - but a tab added to the storefront later is no longer left without a focus indicator.
- The admin cards have their shadow back. `@wordpress/theme` 2.0 removed the elevation property the cards read, and an undefined custom property is not an error - the shadow was simply dropped. It now comes from `@wordpress/base-styles`, where the documented levels still live. A font weight lost to a renamed token is restored the same way.
- The admin's text fields moved off the `@wordpress/components` controls upstream marks not-recommended, onto their `@wordpress/ui` replacements; the connection explainer uses the framework's modal, which traps focus, returns it to the button that opened it and honours reduced motion.
- The post-type sections on the Indexing tab are now collapsible cards, and the headings under them read in order. The old panels drew an `h2` inside the tab's `h3`, so a screen reader's outline went up a level on entering a section.
- The admin's entrance animations honour `prefers-reduced-motion`. Motion only reads that setting when asked, and nothing asked, so they ran for people who had told their system not to show them.
- The DataViews stylesheet behind the sync history table is loaded once instead of twice, and now matches the installed package: one copy was current, the other was from a release older than the table it styled.
- Keyboard focus on the storefront search is a visible 2px ring rather than a sub-pixel hairline against the accent border, and a disabled button there now looks disabled rather than like a live call to action.
- **The search icon has a name for screen readers.** Its only name was the block's placeholder text, which is optional and empty by default - so the default trigger was a button announced as just "button", on every site that left the placeholder blank. It now falls back to "Search", translated.
- A link to the General settings tab opens it. The tab is built from the settings schema, which arrives after the page loads, and the screen fell back to Sync the moment the requested tab was missing - before it could exist. Every link to it, and every reload while on it, landed on Sync.
- Each general setting says its name and description once. The card header already carried both, and the control repeated them beneath it; a switch now sits on its title's row, its own label kept for screen readers only.
- Fixed a JSON setting corrupting itself as it was typed in. Every edit passes through invalid JSON on its way to valid JSON, and the half-typed text was stored and then re-quoted on the next keystroke. The field now holds what is being typed and only applies it once it parses. No setting of this plugin uses it yet; the next one would have.
- **A photo search shows the photo it is searching with.** For the seconds it takes, the results column said "Results" over a skeleton with nothing tying it to the upload; it now shows a thumbnail and "Looking at your photo…", then keeps the photo beside the tags it produced. The tags used to render above the recent searches and push them down; they belong to this search, so they sit in its column. A photo that cannot be read returns to browsing with the notice, instead of leaving half the modal empty.
- **The quiz is usable from the keyboard and a screen reader.** Each answer replaced the button that was pressed and focus fell to the page body, so nothing announced the next question. Focus now moves to each new step, which is a heading, and Back and Start over sit beside the result count rather than a full modal-width away from the "go back a step" message they answer.
- **On a phone the results come first.** Stacked in one column, the recent and popular searches sat above the results, so at 320px a submitted search changed nothing visible. With a search on, narrow screens show the results first and the helpers after them - in the DOM, so keyboard focus follows the same order.
- The default accent colour passes contrast wherever it is text. - On a touch screen the carousel's page dots are 24px targets (the dot itself is unchanged), the popular searches no longer scroll inside the scrolling modal, and the assistant and price fields are large enough that iOS does not zoom in on them.

- In submit mode the highlights stay on screen while a query is typed but not yet searched, instead of their title over a skeleton that never finished loading.

Crossing the 782px breakpoint no longer resets the results carousel, and keeps focus and the caret in the assistant's message field.
- A quiz whose final search fails no longer announces "0 matches" for answers that were never searched.
- Product-row carousels ("You may also like", category listings) show their page dots; the dots were only drawn inside the search modal, so on a phone those rows had no paging control at all.
- A full sync now removes every document this site put in the index that is no longer indexable, whichever sync pushed it. The clean-up only knew about documents the last completed full sync had pushed, so a post first indexed by the incremental sync after an edit, and later taken out of the catalogue without being saved again, stayed searchable until someone next saved it. That covers changing the product mapping or "only visible products", turning on WooCommerce's "Hide out of stock items", disabling a language or a content type, and a status written straight to the database. A forced re-sync did not remove it either. The clean-up now also reads the per-post sync record both syncs write. That record also lets a full sync retry a removal the incremental sync could not complete, as long as the post itself still exists (in the trash, say).
- A permanently deleted post now leaves search even when the incremental sync's request to remove it fails. That request was never tried again: the change left the queue whatever the answer, the post's sync record was deleted along with the post, and a document only the incremental sync had pushed was not in the last full sync's record either, so nothing still said it was in the index and it stayed searchable for good. A failed removal is now kept, per site, until one succeeds, and every full sync retries it, the daily scheduled one included. The change still leaves the incremental queue at once, so a document the service keeps refusing cannot hold up the edits queued behind it. A post restored from the trash and published again is not removed on the strength of an old failure.
- A document a full sync could not remove is now retried by the next full sync even when nothing else still says it is in the index. The clean-up worked from the record of what the last completed full sync indexed, and every full sync replaces that record with what it indexed itself, so a document the service refused to remove dropped out of it after one attempt. That happens when a content type is turned off and its posts are then deleted permanently: the incremental sync ignores a type that is no longer indexed, and a deleted post takes its sync record with it, so only the full sync's record still named the document, and after one refused removal it stayed searchable for good. A removal the full sync's clean-up could not complete is now kept with the incremental sync's failed removals, per site, and every full sync retries it until one succeeds. The clean-up still moves past it at once, so a document the service keeps refusing cannot hold up the rest of the run.

## 1.0.3

- Documented the external service the plugin talks to, as wordpress.org requires: what is sent when you sync, when a visitor searches, and when the AI assistant is used, with a link to the privacy policy.
- The package now carries the JavaScript sources alongside the built bundles, so the compiled assets can be checked against their source.
- Updated the webhead plugin framework to 1.2.0. The distributed package no longer carries development tooling: `symfony/console` (~1.7 MB) and the framework's scaffolding CLI (~590 KB across 61 template files) were bundled but never loaded at runtime. The prefixed dependency bundle drops from 3.7 MB to 1.3 MB.
- Front-end requests no longer scan the plugins directory. The framework resolved declared plugin dependencies on every request to build admin notices and a Site Health field, which outside wp-admin means globbing the plugins directory once per dependency; notices are now built only in wp-admin and the diagnostics field is deferred.
- Fixed the bundled WP-CLI commands (`cache`, `capabilities`, `jobs`, `upgrades`) declaring `--yes` as a required flag, which made WP-CLI reject the very flag it told you to re-run with — leaving those commands impossible to run.
- The AI assistant's message field now has its own border-radius control, in both the block editor and Elementor.
- The AI Assistant tab and its conversation can now be styled like every other part of the widget, in both the block editor and Elementor: tab colours (text, active, underline, divider), the assistant accent and reply text, and your-message bubble colours. 
- The frontend filter list is capped in height and scrolls instead of stretching the modal when a field has many values; the cap is themeable per placement (default 132px).
- Fixed the storefront search and AI assistant showing English on a translated site. Every source file has to be listed in the script translation map for its strings to reach the browser, and the files added by recent features never were — so the whole assistant surface stayed English no matter how complete the translation was. All six missing files are mapped, the German translation is filled in for all 36 storefront strings, and a test now fails if a file with translatable strings is left out of the map.
- Reworked the assistant's waiting state. A bare spinner said only "something is loading"; it now says **Thinking**, with a shine travelling through the word and three dots rising in turn, so a wait of several seconds looks alive. Both stop for visitors who prefer reduced motion.
- The send button's arrow was sitting high and right of centre, and when disabled it was filled the same colour as the composer, so it vanished and left a grey arrow floating in the field. The glyph is redrawn centred and the disabled state is now a visible button.
- The conversation is anchored to the bottom of the pane, like every messenger, instead of clinging to the top with a large empty gap above the input.
- A failed answer now appears as a message from the assistant — same avatar, in a tinted bubble — with a **Try again** action that re-sends the question instead of making you retype it.
- Removed a group of orphaned options on upgrade. An earlier sync and onboarding flow kept its progress in standalone options — a discovery counter and status, initial-sync flags, several "last run" timestamps and a sync interval — which nothing has read since the current engine moved all of it into the sync-runs table. They lingered in the options table, where a value like a discovery status still reading "running" looks like live state. The opt-in "delete my data" uninstall path clears them too, for sites removed without ever reactivating.
- The Search Config tab now covers the whole of Search Cloud's search configuration. Merchandising rules (pin products to the top of a search, keep products out, show a banner) and the three site-level switches — AI search with its index status, AI visual tagging, and ranking by what visitors click — were only editable in the Search Cloud panel; the API exposes them now, so they are editable here too. A switch your plan does not include is shown but disabled, with the reason.
- Fixed click-through tracking never recording anything. The beacon sent a JSON body, which is not a CORS-safelisted content type, so the browser had to preflight it — and the API answers preflight requests without any CORS headers, so every click was blocked before it left the page. The beacon is now form-encoded, which needs no preflight and which the API reads identically.
- Fixed a sync that could stop dead with no way back: the follow-up worker tick was only scheduled at the very end of a tick, so a tick killed part-way through (a slow API against PHP's `max_execution_time`, an out-of-memory, a restarted worker) left the run on "Running" with nothing left to advance it — and because a run in that state holds the single active slot, every later scheduled sync silently did nothing. A tick now arms its successor before it starts working, and the scheduled sync revives a run whose worker has died instead of skipping it.
- Ticks are now time-boxed (20 seconds by default, filterable with `webhead_search_cloud/sync/tick_budget`) rather than bounded only by a batch count. Removing stale documents costs one request each, so a large clean-up could previously run hundreds of blocking requests in a single tick and be killed part-way through.
- Documents the index refuses to delete are now counted and reported on the sync run instead of being dropped from the queue in silence — a failing delete endpoint used to look exactly like a healthy clean-up, with "deleted 0" and no explanation.
- Incremental syncs now say why they failed. A failed incremental run was written to the history with no reason at all, and a rejected push that wasn't a plan-limit recorded nothing whatsoever, so the dashboard showed either an unexplained failure or no sign of a problem at all.
- Removed the leftover `webhead_search_cloud_site_id` option on upgrade. Nothing has read it since the connection moved to key-relative endpoints — the connection screen reads the id straight from the API — so all it did was go quietly stale and mislead anyone inspecting the options table (one site still held `5` while the API reported `4`).
- Fixed sync history retention never deleting anything: the purge built a comparison query the database layer then rejected, so the runs table grew without bound however the retention setting was configured.
