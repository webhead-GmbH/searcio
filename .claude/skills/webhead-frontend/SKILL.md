# webhead Frontend

Frontend UI can run inside aggressive theme, page-builder, and Elementor CSS. Treat frontend rendering, scoped reset CSS, asset loading, responsiveness, and accessibility as one contract.

## Source Paths

- `includes/Admin/Settings_Page.php` registers the admin screen, enqueues assets, and localizes runtime config.
- `includes/Settings/Plugin_Settings.php` defines the settings schema that the UI and REST layer reuse.
- `src/components/Default/index.js` and `src/components/Default/default.scss` define shared card variants and admin shell tokens.
- `src/components/Default/frontend-reset.scss` defines the scoped reset for frontend-only React surfaces that render WordPress components outside wp-admin.
- `src/admin/settings/index.js` boots the settings surface.
- `src/admin/settings/components/SettingsPanel.js` owns the settings shell.
- `src/admin/settings/components/tabs/SettingsGroupTab.js` owns settings field cards and second-level card styling.
- `src/settings/store/context.js` and `src/settings/store/provider.js` own the React settings data flow.

## Rules

- Build frontend UI with WordPress React and WordPress component packages. PHP should render only the mounting container, data attributes, and fallback content when needed; do not hand-build the interactive UI as raw static HTML.
- Wrap frontend React roots in `ThemeProvider` from `@wordpress/theme` with the brand's black (`color={ { primary: '#101010' } }`) and without `isRoot`, which would write the plugin's colours onto the whole page of the theme; import `@wordpress/theme/design-tokens.css`, import WordPress package styles such as `@wordpress/components/build-style/style.css` and `@wordpress/dataviews/build-style/style.css` before the scoped reset, and import `src/components/Default/frontend-reset.scss` from the frontend entrypoint that owns the UI. `@wordpress/ui` has no stylesheet to import: its styles come with its components.
- Keep webpack configured so package CSS imports are bundled, not emitted as script dependencies such as `wp-components/build-style/style.css` in `bundle.*.asset.php`.
- Mount frontend apps inside a scoped root such as `<div data-webhead-frontend-root>` so reset rules cannot leak into the theme or other plugins. Mount every root the page holds (`document.querySelectorAll`): a shortcode or a block can be on a page more than once.
- Keep `frontend-reset.scss` unlayered. Do not wrap it in `@layer`; Elementor, themes, and page builders usually emit unlayered CSS that would outrank layered reset rules.
- **Every rule of the reset weighs more than what a site writes.** A site's stylesheet is written for the whole page and outside any layer: a theme's `button {}`, Elementor's Site Settings as `.elementor-kit-7 input:not([type='button']):not([type='submit']):focus {}`, a designer's `#content a {}`. The reset is weighed against it by specificity alone, so the first part of each of its selectors ends with `$lift`, which is `:is(*, #webhead#webhead)`: it matches every element and weighs two ids, of an id no element has. Write a rule with the file's own variables, `#{$root}` for the root, `#{$scope}` for the root and the overlays and `#{$page}` for `body`, and never with the bare attribute. Do not use global selectors or `!important`: that would outrank the plugin's own stylesheet as well. A site's own `!important` still wins, and nothing short of another one stops it.
- WordPress popovers, dropdowns, menus, modals and DataViews Appearance panels are drawn through portals at the end of `body`, outside the frontend root. `$scope` holds them with the root (`$overlays`: the popover and its container, the modal's overlay, the tooltip, the snackbar list and the slot `@wordpress/ui` draws its overlays in), always under `body:has([data-webhead-frontend-root])`; do not add unscoped body-wide resets.
- **What a site writes on an element is taken off, not painted over.** `all: revert-layer` in a rule outside a layer sets every property back to what the cascade layers say. For an element of `@wordpress/ui` that is its whole design, because that package's styles are in a layer; for an element with no class it is the browser's own style. The rule reaches an element with no class, an element whose class is a CSS module's (`<hash>__<name>`, as every class of `@wordpress/ui` is) and a button or a field of `@wordpress/components` that the package's stylesheet styles whole. Two things follow for a surface. An element with no class is the browser's inside a root, so a rule the plugin writes for `p` or `h3` under a class of its own does nothing: give the element a class that begins with `webhead-search-cloud-`, and the reset leaves it to the plugin. And do not pass a `className` of the plugin's to a control of `@wordpress/ui`: the reset then takes the control for the plugin's and leaves it to the theme. Wrap it in an element of the plugin's instead.
- **The reset loads the stylesheet of `@wordpress/components` a second time, under its scope.** What the package says about a button, a field or a menu item then outranks what a site says about `button`, `input` and `a`. The entry still imports the stylesheet plain, for the popover, the modal and the tooltip themselves, which are outside the scope. It costs a page that prints a surface 18 KB more, compressed (335 KB as written). The stylesheet of DataViews is not loaded a second time: a table on a frontend keeps the rules the reset states for it by name.
- **A control `@wordpress/components` styles when it runs is held by name, and only for what is named.** Such an element carries a class that begins with `css-`, its rule has one class, or the same class three times, and a theme's `button {}` or Elementor's rule for a field outranks either; nothing gives a rule written at run time more weight. The reset says again, by name, what a site reaches of the label of a field (`BaseControl`), the field of `InputControl` and what is built on it (`SearchControl`, the number of a `RangeControl`), an option of `ToggleGroupControl` and the slider of `RangeControl`, as WordPress 7.1 draws them at the default size. `CustomSelectControl`, `UnitControl`, `ColorPicker` and the rest of what the package styles this way are not held: measure one under a customized Elementor kit before a surface uses it, and prefer the control of `@wordpress/ui`, which the rule above holds whole.
- **The root states its own text and is drawn on its own background.** Everything a page hands down is stated on the root: colour, family, size, weight, slant, spacing of letters and words, alignment, indent, shadow, capitals. A surface in an Elementor Text Editor widget that is centred, italic and in capitals reads as it does on a plain page. The background is the design system's white, because the text is dark and a section of a page can be any colour. That rule has no weight (`:where()`), so a class of the plugin's on the root takes it away; a surface that does so gives the provider the colour it stands on, `color={ { primary: '#101010', bg: '…' } }`. The reset adds no padding: a surface that wants air round it sets its own, or is a `Card`.
- Do not add generic frontend rules such as `svg { display: block; }` inside the reset. WordPress UI components may render decorative SVGs that are intentionally hidden by package CSS, such as `Tabs.Tab` chevrons.
- The reset may neutralize hostile theme/page-builder borders, radii, shadows, text transforms, and button appearance, but it must not resize DataViews search fields or replace WordPress component styling with bespoke product CSS.
- **A reset rule states the enabled state, so it must state the disabled one too.** Every scoped selector here carries at least two attribute selectors, which outranks the package's own `:disabled` and `[aria-disabled='true']` rules — so writing only a base colour silently deletes the disabled appearance rather than leaving it alone. A disabled Button kept its full brand-coloured label and ring, and the only remaining cue was the mouse cursor. Whenever you set `color`, `background` or the ring on a control, add the matching `:disabled, [aria-disabled='true']` rule beside it, and remember the package's disabled `border-color` can never reach these controls because the reset zeroes `border` — state the disabled ring the same way you stated the enabled one.
- **Keep the package's `:not(:disabled)` guards when you copy a rule.** The checked fill for checkboxes and radios is guarded on purpose. Dropping the guard filled a *disabled* checked box solid brand colour, identical to a live one.
- **Focus is an `outline`, not a shadow.** `outline: 2px solid transparent` paints nothing, and pairing it with a `box-shadow: 0 0 0 0.5px` spread leaves a sub-pixel hairline hugging the field — invisible against an accent-coloured border, and below what a focus indicator needs to carry. Draw the real thing: `outline: var(--wpds-border-width-focus) solid var(--wpds-color-stroke-focus)`, never the accent, which is the brand's black and no ring at all round a black button, with a matching `outline-offset`. This is a keyboard-only regression, so nothing about it appears in a screenshot of the page at rest — tab to the control and read `getComputedStyle(el).outline` with the element actually matching `:focus`.
- **`@wordpress/ui` styles are in a cascade layer, and the reset is not.** A rule outside a layer outranks every rule inside one, whatever its specificity. The reset's rule that sets a theme's `button` and `input` colour back used to reach those controls too: a filled `Button` from `@wordpress/ui` had its label in the text colour, dark on a dark fill. It names what it is for now: a control with no class, and the controls of `@wordpress/components` and DataViews. Before you add an element-level rule, read what it does to a `@wordpress/ui` control with `getComputedStyle`. What a theme writes outside a layer outranks that package in the same way, which is what `all: revert-layer` is in the reset for.
- **A custom property set on the frontend root does not reach what a theme provider wraps.** The provider writes its own values inline on its own element, below the root. The reset sets the brand in three places for that reason: on the root, on `[data-wpds-corner-radius] > *` (what a provider wraps) and on `body:has([data-webhead-frontend-root])` for menus and popovers.
- **A surface is the same on every site, and that is measured, not assumed.** Most sites this plugin is installed on are built with Elementor, on a kit a designer has customized, and a site writes `button {}`, `label {}`, `a:focus {}` and `input[type='radio']::after {}` outside any layer. Before the rules above, measured on a surface with the controls of both packages under the Hello Elementor theme with a kit customized as far as Site Settings go: a `Button` of `@wordpress/ui` was red with a dashed border and 100px tall, a label orange, 26px and in capitals, a field yellow with a double border, a link pink and overlined, and in a Text Editor widget on a dark section the text was centred, in capitals, with a red shadow, and dark on dark. With them, on 2026-10-03, every property of every element of that surface, of its menu and of its dialog reads the same with such a site's stylesheet on and off. What is still the site's: a declaration it marks `!important`; an underline or a strike set on a container the surface is in, which is drawn through every line inside it and cannot be taken off from within; how the browser smooths letters (`-webkit-font-smoothing`); and the controls `@wordpress/components` styles at run time that the reset does not name. Do not work round one of these in the surface's own stylesheet: say what you measured.
- **Elementor keeps the output of most widgets, and a surface in one is still run.** Its element cache (Settings → Performance, on by default) keeps a widget's output for a day and prints it on later visits without running the widget: a shortcode in a Toggle, a tab or an accordion printed its root on every visit and its script and stylesheet on the first one only. The framework tells Elementor that an element which holds a shortcode registered in `register_shortcodes()` is run on every visit; one added with `add_shortcode()` directly is not covered. The Shortcode and Text Editor widgets are run on every visit by Elementor's own rule. A widget whose own cache setting is switched to Active in the editor stays cached, markup and all, and prints no script: that setting is the site owner's and is not overruled.
- **A caching plugin runs a surface late and a consent plugin runs it later, and that has to be all that happens.** Measured on 2026-10-04 under WP Rocket 3.23 (delay, defer and minify on), Borlabs Cookie 3.4 and WPML 5.1 with German and English. WP Rocket's "Delay JavaScript execution" holds every script of a page until the visitor moves the mouse, scrolls or touches, so a root is empty until then: print fallback content or a height from PHP where an empty space on load matters. Its "Load JavaScript deferred" gives every script file `defer` and leaves the line WordPress prints after a file where it is, so `wp.date.setSettings()` ran before `wp-date` had loaded and a surface showed the dates of an English site in UTC: the asset registry answers `rocket_exclude_defer_js` with the entry and everything it depends on, on a page that registered one. Borlabs Cookie's Script Blocker turns the entry's `<script>` into a template until the visitor agrees, and runs it then, after what it depends on, which is not blocked. So an entry mounts when it is run, at once or through `@wordpress/dom-ready`, and never on a `DOMContentLoaded` listener of its own, which by then has long fired. On a page WPML translates, `wp.date` and the translations WordPress prints for its own scripts follow the language of that page. Not measured: WP Rocket's "Remove Unused CSS", which needs its service to reach the site and removes rules that match nothing when it reads the page, before a surface is drawn; expect a site that uses it to need the plugin's stylesheets in WP Rocket's safelist.
- Enqueue frontend JavaScript and CSS only on pages where the design exists: block render callback, shortcode callback, widget render path, or a similarly precise detector. Do not enqueue frontend bundles globally.
- Enqueue through the plugin's asset registry, from the code that prints the markup: `$plugin->get_assets()->enqueue( 'frontend.cards' )` for a webpack entry's script with its stylesheet, `enqueue_style( 'frontend.cards' )` for the stylesheet alone. Inject it into a service as `Webhead\WP\SearchCloud\Dependencies\Webhead\WP\Framework\Assets\Asset_Registry`. It reads the entry's `.asset.php` manifest once, registers the handle with the dependencies, version and script translations the build recorded, and answers `false` for an entry that was never built. Set extra dependencies, a loading strategy or page data with `configure()` and `localize()` before the first enqueue; give `localize()` a closure so the data is only built on a request that prints the script. A package's stylesheet is named `style.css`, and the build writes anything of that name to a file of its own, `public/style-<entry>.css`; the registry registers both and prints that one first, so the reset follows the package whatever order the two were imported in.
- A shortcode that prints a surface is a class in `includes/Shortcodes/` that extends `Webhead\WP\SearchCloud\Dependencies\Webhead\WP\Framework\Shortcodes\Abstract_Shortcode`, takes the registry as its constructor argument (`$container->add( 'cards_shortcode', Cards_Shortcode::class )->addArgument( Asset_Registry::class )`), enqueues in `render()` and returns the root. Register it in `register_shortcodes( Shortcode_Manager $shortcode_manager, Container $container )` in `includes/Plugin.php`. When the plugin was generated without the shortcode scaffold that method is not there yet: add it, and it overrides the framework's, which is empty.
- An entry is a line in `webpack.config.js`; `composer framework:update` keeps the entries this plugin added. Built files land in `public/`.
- A block's `render.php` is a bare file WordPress includes. When it has to reach the plugin it asks for the running instance: `\Webhead\WP\SearchCloud\Plugin::instance()?->get_assets()->enqueue( 'frontend.cards' )`. Prefer a block provider with a `render()` method, which the container builds with the services it needs.
- Recheck frontend screens in a real browser after every UI change because themes, Elementor, WooCommerce, and caching plugins can override component CSS. Verify normal, hover, active/pressed, selected, disabled, and focus-visible states for buttons, tabs, DataViews controls, search/filter controls, checkboxes, radios, text inputs, textareas, selects, range/number controls, notices, and layout components.
- Verify responsive behavior at desktop, tablet, and mobile widths. The page must not introduce horizontal overflow, clipped controls, overlapping text, broken focus outlines, or unscrollable panels.
- Accessibility must be treated as a release gate: keyboard navigation, visible focus, semantic labels, control descriptions, color contrast, reduced-motion behavior, and screen-reader names should reach a 100% automated audit where the project has an a11y runner.
- Keep data-backed frontend lists server-driven. JavaScript may map view state to REST query parameters, but search, filtering, sorting, and pagination should not be performed only in the browser for server datasets.
- Use plugin-specific REST namespaces, nonces, capability checks, escaping, sanitization, and translation functions exactly as in admin surfaces.

## Delivery

1. Update the PHP side first: menu registration, asset enqueueing, localized config object, and permissions.
2. Update the settings schema second: `includes/Settings/Plugin_Settings.php` and related manager usage.
3. Update the React side third: keep the shell in `SettingsPanel.js` and split each tab or major section into its own file.
4. Use `@wordpress/ui` recommended primitives; every `Card.Header` title must use `Card.Title` with the correct semantic `render` heading.
5. Use `@wordpress/dataviews` for admin tables, map search/filter/sort/pagination to REST or server query parameters, and mark decorative fields with `filterBy: false`.
6. Apply the shared card variants by nesting depth: default for top-level cards, dotted for second-level cards, secondary for third-level cards, and grid only for intentional alternate surfaces.
7. Use documented save/submit, destructive-action, Badge, Tabs, Tooltip, form-control, and motion-token patterns instead of local ad-hoc UI behavior.
8. For frontend React surfaces, import `src/components/Default/frontend-reset.scss` only from the frontend entrypoint, mount inside `[data-webhead-frontend-root]`, and enqueue assets only where the UI exists.
9. Run `npm run build`, run the browser smoke check when available, and manually open the changed admin or frontend screen after the change.

## Verification

- Run the affected PHP and JavaScript tests.
- Run `npm run build` after frontend asset changes.
- Open the exact frontend page that contains the design in a browser, not just wp-admin.
- Open it on a site that styles its own page: under Elementor with the Hello Elementor theme, with Site Settings → Typography, Buttons and Form Fields set to values nobody could miss, in a Shortcode widget and in a Text Editor widget on a dark section, and under a classic theme (`wp theme activate twentytwentyone`). Read `getComputedStyle` of a filled button, a label, a field and a link in keyboard focus, for a control of each package, and compare with the same page under a block theme: they are the same, or the surface uses something the reset does not hold.
- Ask for that page three times as a visitor who is not signed in, and read the HTML each time for the root, the script and the stylesheets. Elementor's element cache answers the second and the third.
- Capture or inspect desktop and mobile screenshots when changing layout, reset CSS, or component composition.
- Run an accessibility audit when available and fix failures instead of documenting them as known issues.
